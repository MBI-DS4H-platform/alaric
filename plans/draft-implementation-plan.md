### Requirements that supersede older implementation sketches

- Start the fit and its downstream work on entering stage 3; committed stage-2 range edits start no library work while the stacking selection is inactive. A stale but still active selection restarts the fit at stage 2 (ST §7.2a); the author rejected a stage-3-prefix gate (I6).
- Prepare/reference-cut the complete RNA independently of the fit. Open stage 4 once its fragments are known; fitting may continue while the user types thresholds.
- Compute all fits, tables and energies on the full RNA. Clip only derived selections, displays, jobs and downstream hand-offs.
- Stage 4 owns the clip. Stages 5–6 show it read-only. Adapt a saved matrix once on Continue 4→5; do not rewrite it on each clip edit.
- Use `null` for undecided stage decisions, keyed stacking selections, decision bases, and active/inactive markers. Computation state never moves the stage.
- Score both ligand sets in one Alaric run per protein range. No grids, JAX or summed-range energies enter preparic's scoring path.
- Derive RMSD and energy thresholds in Alaric using the smallest multiple of 0.01 strictly above the delivered raw value. Keep raw values for validation; do not display them. Gaussian cutoffs instead use the prior deliverable's floor to five decimals and `score >= cutoff` acceptance.
- Use one all-filter check whose jobs do not depend on editable Gaussian classes. Both anchor modes will eventually be exported.
- Consume the precomputed Gaussian JSON and installed caches. Keep each prefilter variant's parent cutoff, apply the JSON's strict d < 5 Å / φ < 60° mask, identify arrays by `npy_sha256`, and fail visibly on a bad installation. The offline generator and its gitignored caches are prerequisite deliverables, not preparic startup work.
- Run transformations through eight local spawn workers, without a persistent result cache, hashserver or database. Restart restores mounted decisions/CIF and the same stage, then recomputes required results. Only mounted cells survive; correctness is required only if the browser restarts right afterwards (O6).
- From stage 4 on, the viewer shows only the backend's aareduce range PDBs, byte for byte as generated, with fragment overlays on top; the RCSB structure is shown in stages 1–3 only (P11, author decision).

## 4. W1 — shared-project foundation in preparic

### Durable input and decision graph

- Mount all decisions file-authoritatively, including CIF. The backend startup loader initializes undecided markers to `null`, and clip to `(0,0)` with its basis. No running transformer writes a decision cell.
- Before the loader resets malformed content, keep its diagnostics. A stored decision without a basis loads as undecided, with an explanation, and is never migrated silently (author, I7).
- Implement pure stage derivation and decision/read validators. M2/M3/M4/M5/M6 are ranges, keyed stacking selection, threshold table, addressed interaction matrix and Gaussian classes. Like the clip, the energy-threshold table S24 is a stage parameter, not a marker (D13). Retained markers can be inactive; all consumers treat inactive or inapplicable decisions as undecided.
- Separate marker presence/well-formedness from forward-gate readiness. In particular, stage 4's valid skeleton contains blank thresholds; it must remain stage 4 while those blanks are filled. Backend validators accept undecided and distinguish permitted blanks from malformed numbers.
- Implement bases and restoration according to the oracle's decision-specific rules. Thresholds and clip belong to PDB code + range 1; energy-threshold edits too, and each protein range's values also to that range's row, not its index (D13); matrix restoration additionally checks selected anchors and adapts its extent; classes belong to selected stacking keys. Carry the relevant project/range identity through nested lineage so identical row/key values from another project cannot reactivate unrelated decisions.
- Keep computational identity separate from restoration basis. A code/library refit preserves appropriate user edits while changing the computed results and diff marks.
- Add no entry lineage: the author rejected activation tokens and parent-token linkage (I1). Keep ST's semantic bases, active flags and ordered orphan cleanup; protection against racing tab actions lies outside the weakened guarantee (O7/D17).

### Execution and restart policy (author decision; D14 resolved)

Configure preparic's Seamless backend at startup for **eight local spawn workers**. All transformation delivery forms must work with that setup; keep backend orchestration separate from worker computation. Choose module attachments or staged CLI wrappers based on W0's spawn probe. Alaric bash steps may still select their declared worker environment, but they must not bypass preparic's worker scheduling or introduce another execution service.

Disable persistent result/buffer caching and hashserver/database connections; startup must not depend on those services being installed or reachable. In-memory reuse/deduplication during one live backend may be used where supported, but no acceptance condition relies on retaining those results after restart. Process-count and worker-state differences must not affect scientific output. Exercise queued and superseded work under the eight-worker setup rather than relying on the old in-process lock behavior.

Persist decisions, CIF and required project files through mounts. Installed fragment libraries and precomputed Gaussian arrays are scientific inputs, not Seamless result caches, and remain on disk. Only mounted cells survive a restart, and correctness is required only if the browser restarts right afterwards; a tab kept open across a backend restart has undefined behavior (author, O6). After restart, recompute required transformations from those files: from stage 3 onward this includes fit, tables and scoring. Their library loading can take minutes; keep the restored stage stable, show pending wording, and close freshness-dependent gates until results return. Stage 4 may remain editable while results recompute. Do not recover old computed output mounts as fresh merely because their decisions match.

### Writes, navigation and synchronization

Centralize writes in the client integration layer, with the stage at issue time, original target revision, pending value and acknowledgment state. Send writes through `seamless-client.js`, with its own retries: the author rejected a separate write adapter with markers frozen per intent (I3). Make no assumption about withdrawing a write already handed to the client. After a disconnect, cancel app-owned debounce work, reread, and queue a write of the correct state before issuing new actions (ST §7.2a, §11.11). Handle acknowledgment, including equal-value success without an update. Inline edits are optimistic; losing/conflicting writes adopt the accepted server state and notify the user. Debounced edits are dropped if their stage, connection or remote target revision changes before application. Put no defaults/resets in observers of absent computed values. Test already-in-flight and ambiguous HTTP outcomes; cancellation alone is not a consistency guarantee.

Implement Continue/Back as explicit actions. Continue rechecks its gate immediately before sending, restores/merges/defaults the next marker, and performs required orphan cleanup and stale-clip reset in the proven order. Add no commit-time admission mechanism: the author rejected it as too complex and weakened the gate guarantee, which holds only if tabs do not race (D17, O7). When tab A presses Continue while tab B is not editing, B must proceed to the next stage as if it had pressed Continue too. Back deactivates the current marker under D1. Under the per-marker design, normal transitions write one marker; exceptional cleanup is awaited and aborts on conflicting state. Never arm Continue to execute when computation later finishes. Resolve lost acknowledgments by reading the installed value after resynchronization, not by resending with a new marker. Add no write-generation fence: a write from a tab kept open across a backend restart is outside the contract (O6).

Stage 1 retains the code/CIF two-write exception: download successfully first, commit code and matching bytes, and validate the entry id read from the stored CIF via S21. Implement and test the arbiter rule, including retry after a CIF conflict only while that commit still owns the winning code and stage. Until consistency is established, close 1→2. A failed download changes neither decision.

On load/reconnect, hold a read-only overlay until every required decision has been read, including the stored structure through an explicit read when the viewer needs it. Clear trust in old computed shares on reconnect and reread them before they can become fresh; after a backend restart the browser reloads (O6). A viewer showing an independent RCSB download is insufficient to prove it shows the persisted bytes; use the persisted structure for restoration and check its identity. From stage 4 on, the viewer does not show that structure at all: it waits for a fresh reread of S23 and shows "preparing all-atom structure…" until then (P11). URL parameters apply only under P9's stage-1/empty-code rules.

### Results, execution gating and errors

Use a common result envelope carrying `schema`, payload and enough input lineage to compare against the tab's current decisions, including optimistic edits. Echo actual relevant inputs through the computation; do not attach whatever decisions happen to be current when an old result arrives. Include structure identity and protein range identity wherever they affect results. Result freshness must also account for the current code/data lifecycle established in W0. The author rejected a cross-result model/ring content identity (I5). Rely on `filter_set_version`, declared dependencies and the delivered data identities (`spec_digest`, `npy_sha256`); there is no browser model (O5). Ordinary pinned source/library updates should use the documented restart/resynchronization lifecycle.

State-graph status explains pending/failed/blocked results; it never certifies freshness or advances the stage. The author rejected validation receipts (I4): add no receipt shares, and leave T10/T19/T27 results unshared. Keep backend validation and its error reporting as a second check. The 4→5 and 5→6 gates still require T10 and T27, respectively, not to have failed, read from the state graph (author, kept after I4).

Implement the P6 stage-to-error mapping centrally, including T24 and installation errors. Suppress failures before the first status snapshot and while this tab has pending input writes. Show conversion failures as blocked. Later-stage work running on retained or orphaned decisions must not leak banners into earlier stages.

Gate the fit branch on S8's `active` flag, as ST §5.3 decides; the author rejected gating it on the valid stage-3 prefix (I6). A stale but active S8 after a range change therefore restarts the fit while the stage is 2 (ST §7.2a). Changing ticks within stage 3 must not change A1's numerical identity or repeatedly launch the fit: the gate reads only the `active` flag, and the fit's inputs remain the RNA, exclude and library identities.

**Exit:** two tabs agree on stage/decisions after propagation; when one tab presses Continue and the other is not editing, both reach the next stage; the eight-worker spawn setup works with hashserver/database absent; a backend restart followed by a browser restart preserves decisions and stage without browser repair and recomputes results (O6); no result is trusted before resynchronization; without racing tabs no transition skips a gate (O7).
